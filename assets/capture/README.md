# Screenshot capture

Four images, three of them reproducible with one script. Everything in this folder exists
so that the README's visuals can be **regenerated** instead of being a one-off paste that
nobody can update.

```
assets/
├── orafabric-logo.png              export from the brand source, not from here
├── demo-01-tools-loaded.png        ✔ rendered from a real verify.py run (checked in)
├── demo-02-config-copy.png         requires your login — see shot 2
└── demo-03-evidence-panel.png      ✔ rendered from a real retrieval pack (checked in)
```

Script: `capture.py` — Python 3.9+, no pip installs, needs a Chromium/Chrome binary.

---

## Shot 1 — tools loaded (already done)

`demo-01-tools-loaded.png` is checked in. It was produced from the genuine transcript in
`tools-loaded.txt` (a real `verify.py` run, key redacted), rendered to a terminal card.

To refresh it after a schema change:

```bash
cd assets/capture
export ORAFABRIC_API_KEY=...        # any working key
python ../../examples/01-basic-mcp-connection/verify.py | tee tools-loaded.txt

python capture.py terminal \
  --text tools-loaded.txt \
  --out ../demo-01-tools-loaded.png \
  --title "verify.py — six tools loaded, free coverage call"
```

Why a rendered card rather than a screenshot of someone's terminal: no local paths, no
username in the prompt, no client window chrome, and it can be regenerated by CI. The
content is the real output, which is what the shot is for.

## Shot 2 — the console's "copy MCP configuration" button

This is behind auth, so it cannot be a one-liner. `capture.py console` opens a throwaway
browser profile, lets you log in, then screenshots headlessly using the same profile:

```bash
cd assets/capture
python capture.py console \
  --url "https://orafabric.com/dev/login?next=/dev" \
  --target "/dev" \
  --out ../demo-02-config-copy.png
```

It will: open a window at the login page → you log in and navigate to the developer
console → press Enter in the terminal → it screenshots and exits.

If you prefer the manual route (equally good):

1. open the console, log in;
2. make the **copy configuration** button and the key panel visible in one frame;
3. screenshot the browser viewport at **1280×860** (or crop to it afterwards);
4. **redact**: the key entirely — not a prefix plus last 4, none of it; also your email in
   the top bar, your avatar, and any URL query string;
5. save as `assets/demo-02-config-copy.png`.

This is the single most useful image in the repository: it is the moment the whole
integration becomes a paste.

## Shot 3 — the evidence panel

This is the shot that explains the product in one glance: claim, source sentence,
strength, paper. The checked-in `demo-03-evidence-panel.png` was produced exactly this way
— 60 findings, four kept, two papers resolved with `get_paper` ($0.03 + $0.06). Re-render
it from a **real** pack whenever the schema or the copy changes:

```bash
cd assets/capture

# 1. save one pack (costs $0.03)
python ../../examples/04-python-api-integration/main.py \
  --query "Does metformin improve response to immune checkpoint blockade?" \
  --anchor-a metformin --anchor-b "immune checkpoint inhibitor" \
  --json > my-pack.json

# 2. render it
python capture.py evidence \
  --pack my-pack.json \
  --question "Does metformin improve response to immune checkpoint blockade?" \
  --anchors metformin pembrolizumab \
  --out ../demo-03-evidence-panel.png
```

`--anchors` drives the "connects both anchors" tag: pass two names that actually appear
in the claims you expect to keep. Pick a question where at least one finding connects
both, otherwise every card reads "one endpoint only" and the shot undersells the point.

### `sample_pack.json` is a fixture, not evidence

It exists only so the renderer can be tested offline. Any image rendered from it carries a
red banner reading **SAMPLE DATA — synthetic fixture**. That banner is deliberate: a
fixture must never be able to pass as a real result, and a screenshot is exactly where
that mistake would become expensive.

## Acceptance checklist before you commit an image

- [ ] no API key, not even a prefix, not even partially masked over a readable key;
- [ ] no email address, avatar, account menu, or top-bar user chip;
- [ ] no local file path, hostname, or terminal prompt containing a username;
- [ ] no browser tabs, bookmarks bar, or notifications;
- [ ] no third-party paper text beyond a single quoted sentence per finding;
- [ ] at 1280 px wide it is still readable at GitHub's ~900 px render width;
- [ ] under ~300 KB, PNG;
- [ ] the caption under it in the README says what it is, and does not overclaim.

## Regenerating after a schema change

If a finding key is renamed server-side, the tolerant accessor in `capture.py`
(`field(item, *names)`) still resolves it as long as any of the candidate names exist.
When a field genuinely disappears, fix the accessor, not the screenshot.
